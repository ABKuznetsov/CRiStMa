# Structure Core: symmetry-expanded identity and periodic geometry

Date: 2026-08-30

Status: approved design for an internal milestone

## 1. Purpose

This milestone establishes the finite atomic representation on which geometry,
coordination, polyhedra, diffraction, transforms, and refinement will depend.
It must preserve the distinction between:

```text
crystallographic position
chemical occupation of that position
symmetry expansion within the reference cell
periodic images in translated cells
```

The completed scientific path is:

```text
structure file
     |
     v
CrystalStructure
     |
     v
space-group expansion
     |
     v
AtomicView of unique reference-cell positions
     |
     v
PeriodicNeighborGraph
     |
     v
CoordinationEnvironment
```

This is an internal development milestone, not the public `0.1.0` release.
CRiStMa remains a development package until its API has been exercised by at
least Viewer and Finder on real data. The first public release is prepared only
after those integrations and a public-API stabilization pass.

## 2. Position and occupation model

`IndependentSite` represents one independent crystallographic position and its
occupation model:

```text
IndependentSite
|- id
|- label
|- fractional
|- components: tuple[SiteComponent, ...]
`- displacement
```

Each `SiteComponent` contains a chemical species and its occupancy:

```text
SiteComponent
|- species
`- occupancy
```

The following invariants apply:

```text
0 <= component.occupancy <= 1
sum(component.occupancy) <= 1
vacancy_fraction = 1 - sum(component.occupancy)
```

Direct construction with an invalid component occupancy or a total occupancy
above one raises `ValueError`. Source readers report the same defect as an
error diagnostic before canonical object construction. An affected source
record does not produce a partial `IndependentSite` or a canonical structure
with silently altered occupation.

Vacancy fraction is a derived value and does not create an atom or a special
vacancy component. A site with mixed chemical occupancy remains one geometric
position. A change in component fractions does not change that position's
identity.

`SiteComponent` has no coordinates. Components reported at different
coordinates are positional or split disorder and therefore belong to distinct
`IndependentSite` positions. Future disorder-group types may relate those
positions without changing this invariant.

## 3. ExpandedAtom

Symmetry generation retains both the crystallographic operation and the
integer translation used to normalize its result into the reference cell:

```text
SymmetryImageProvenance
|- operation_id
`- normalization_translation: tuple[int, int, int]
```

The sign convention is explicit:

```text
canonical_fractional
= operation(source_fractional) + normalization_translation
```

For example, `(1.12, -0.04, 0.35)` is normalized to
`(0.12, 0.96, 0.35)` with translation `(-1, +1, 0)`.

`ExpandedAtom` represents one unique space-group-expanded geometric position
inside the reference unit cell:

```text
ExpandedAtom
|- id
|- structure_id
|- source_site_id
|- fractional
|- cartesian
|- components
|- displacement
|- representative_image: SymmetryImageProvenance
`- equivalent_images: tuple[SymmetryImageProvenance, ...]
```

The expansion preserves the occupation model of the source site. Isotropic
displacement parameters are preserved numerically. Anisotropic displacement
tensors are transformed by the generating symmetry operation according to
their coordinate representation, so the expanded ellipsoid has the correct
orientation. Unsupported or invalid tensor representations fail explicitly;
they are never copied as if they were scalar values.

Expansion does not split mixed occupancy into coincident atoms.

A special position may be generated by several symmetry operations. Equivalent
generated positions are merged into one `ExpandedAtom`; every generating image,
including its normalization translation, is retained. `equivalent_images` is
the complete tuple and contains `representative_image`. The representative is
provenance and is not itself the atom's identity.

For a merged special position, anisotropic tensors transformed through every
equivalent image must agree within the declared numerical tolerance. A
disagreement is a symmetry-consistency failure; expansion does not select one
operation's tensor arbitrarily.

Expanded-atom identity is determined by:

```text
structure identity
+ source-site identity
+ canonical symmetry-expanded position in the reference cell
```

Chemical species and component occupancy are excluded from identity. Numeric
canonicalization and tolerance policy are explicit inputs to expansion, so ID
generation is deterministic under that policy.

The existing internal name `ExpandedAtomRef` is replaced by `ExpandedAtom`
before any public release. No compatibility alias is required for the internal
development API.

## 4. PeriodicAtomRef

Space-group expansion and lattice translation are separate operations.
`ExpandedAtom` never represents the infinite copies in neighboring cells.

```text
PeriodicAtomRef
|- atom_id
`- cell_translation: tuple[int, int, int]
```

`PeriodicAtomRef` is a lightweight reference, not an independent atom. Its
fractional and Cartesian coordinates are computed from the referenced atom,
cell, and integer translation. They are not stored in the reference.

```text
ExpandedAtom = which unique reference-cell position
PeriodicAtomRef = which translated image of that position
```

The same reference type may be used by neighbor graphs, polyhedra, supercell
views, and visualization without inserting periodic copies into the canonical
structure or atomic view.

## 5. AtomicPosition and AtomicView

`AtomicPosition` is a minimal structural-typing capability, not a shared
scientific base class:

```python
class AtomicPosition(Protocol):
    id: str
    cartesian: tuple[float, float, float]
    components: tuple[SiteComponent, ...]
```

`ExpandedAtom` and `MolecularAtom` satisfy this protocol as independent
scientific types. `ExpandedAtom` additionally provides fractional coordinates,
source-site identity, displacement, and symmetry provenance. A normal
`MolecularAtom` has one component with occupancy one; the representation also
permits a molecular position with a richer occupation model.

`AtomicView` is the finite, immutable, numerical representation of one
structure at a chosen expansion policy. It is generic in the concrete atomic
position type so specialized consumers retain that type:

```python
TAtom = TypeVar("TAtom", bound=AtomicPosition)

@dataclass(frozen=True)
class AtomicView(Generic[TAtom]):
    atoms: tuple[TAtom, ...]
    cartesian: NDArray
    fractional: NDArray | None
    cell: UnitCell | None
    periodic: tuple[bool, bool, bool]
```

Cartesian coordinates are always present. Fractional coordinates are present
only when physically meaningful. A cell is present only for a cell-based
representation. Every periodic axis requires both a cell and fractional
coordinates. Partial periodicity such as `(True, True, False)` is valid.

The arrays are read-only and row-aligned with `atoms`.
`AtomicView[ExpandedAtom]` contains the unique symmetry-expanded positions of
the reference cell only; periodic images are produced on demand through
`PeriodicAtomRef`. `AtomicView[MolecularAtom]` normally has no cell or
fractional coordinates and has periodicity `(False, False, False)`.

`UnitCell` remains the single scientific representation of a cell. Numerical
algorithms use a read-only matrix exposed by the cell or by an explicit
`AtomicView.cell_matrix` convenience property; `AtomicView` does not introduce
a second canonical cell representation.

The current single-species-per-row representation is removed because it cannot
represent mixed occupancy. Chemical occupation is available through:

```python
view.atoms[index].components
```

An `AtomicView` may still carry additional row-aligned `AtomicPropertyTable`
data. Such derived properties do not replace canonical identity, coordinates,
components, or displacement information.

## 6. Non-periodic and periodic neighbors

Non-periodic geometry uses a finite graph with direct atom-to-atom edges:

```text
Neighbor
|- source_atom_id
|- target_atom_id
|- distance
`- vector_cartesian

NeighborGraph
|- atoms
|- neighbors_by_atom
`- diagnostics
```

`PeriodicNeighbor` describes a directed relation from an atom in the reference
cell to an image of a target atom:

```text
PeriodicNeighbor
|- source_atom_id
|- target: PeriodicAtomRef
|- distance
|- vector_fractional
`- vector_cartesian
```

The source is implicitly in cell `(0, 0, 0)`. A reverse relation has the
opposite vector and the translation required to view the original source from
the target's reference cell.

`PeriodicNeighborGraph` contains a finite node set and explicit periodic
edges:

```text
PeriodicNeighborGraph
|- atoms: tuple[ExpandedAtom, ...]
|- neighbors_by_atom
`- diagnostics
```

Graph nodes are unique geometric positions, not position-component pairs.
Consequently mixed occupancy does not create zero-length edges, duplicate
neighbors, or inflated coordination numbers.

The graph preserves periodic self-neighbors when scientifically valid. Edge
identity includes the target atom and target cell translation, so two images of
the same reference-cell atom remain distinct neighbors.

`NeighborGraph` and `PeriodicNeighborGraph` remain distinct result types; a
nullable translation field is not used to collapse their semantics. Shared
consumers may accept a small `NeighborGraphLike[TAtom]` protocol exposing the
atom collection and neighbor lookup without hiding specialized periodic data.

## 7. NeighborFinder and coordination

The initial configurable tool supports both finite and periodic views:

```python
mol_graph = NeighborFinder(cutoff=2.0).find(molecular_view)
# NeighborGraph[MolecularAtom]

xtal_graph = NeighborFinder(cutoff=3.0).find(crystal_view)
# PeriodicNeighborGraph[ExpandedAtom]
```

For a view with no periodic axes, `NeighborFinder.find()` returns a
`NeighborGraph`. For a view with at least one periodic axis, it returns a
`PeriodicNeighborGraph` and requires a cell and fractional coordinates. Static
typing exposes these alternatives through overloads where the concrete view
type makes the result knowable. Configuration is stored by the finder;
calculation state is returned explicitly.

For a distance cutoff, translation enumeration is mathematically complete for
every valid unit cell, including highly skewed triclinic cells. Bounds are
derived from reciprocal/metric geometry rather than independent estimates from
the direct lengths `a`, `b`, and `c`. An implementation may optimize or cache
the enumeration only if it preserves this completeness guarantee.

The first implementation provides an exact distance-cutoff method. Chemistry-
dependent policies such as covalent radii and bond-valence selection are added
as independent policies after the periodic geometry is verified.

`CoordinationAnalyzer` consumes an atomic view and a `NeighborGraphLike` result
and returns explicit `CoordinationEnvironment` results. Geometric coordination
is computed per position. Chemical interpretations may inspect all
`SiteComponent` values and report weighted component contributions without
altering graph topology.

## 8. Public usage shape

The intended consumer-facing composition is:

```python
from cristma import read_structure
from cristma.geometry import NeighborFinder
from cristma.symmetry import expand_structure

crystal = read_structure("sample.cif")
view = expand_structure(crystal)
graph = NeighborFinder(cutoff=3.0).find(view)
```

Exact convenience names may be aligned with the existing top-level I/O API
during implementation. The scientific return types and invariants in this
document are the stable design requirements.

## 9. Diagnostics and failure behavior

Invalid CRiStMa object construction and programmer errors raise exceptions.
Invalid source data encountered while producing objects is represented by
structured reader diagnostics; the mapper never constructs an object that
violates its invariants. Recoverable scientific conditions encountered during
a calculation are represented by structured calculation diagnostics.

At minimum, diagnostics cover:

- invalid or non-invertible cells encountered in source data;
- source occupancy totals above one
  (`cif.map.occupancy_total_exceeds_one`, or the corresponding reader-specific
  namespaced code);
- incomplete or fallback symmetry;
- positions merged within the selected tolerance;
- ambiguous atom identity after canonicalization;
- cutoffs or search bounds that cannot be evaluated safely;
- non-finite coordinates, distances, or vectors.

No algorithm silently drops a component, symmetry-equivalent position,
periodic edge, or failed calculation.

## 10. Verification

The milestone is complete when tests establish:

- P1 expansion preserves every independent site exactly once;
- general positions expand to the expected multiplicity;
- special-position duplicates merge and retain all generating operations;
- symmetry-image provenance retains the correct normalization translation;
- symmetry-related anisotropic ADPs have the correct transformed tensors;
- equivalent images of a special position either produce consistent
  anisotropic tensors or an explicit symmetry-consistency failure;
- mixed occupancy creates one expanded position with all components;
- split positions remain distinct;
- occupancy totals and vacancy fractions obey their invariants;
- Cartesian and fractional coordinates agree with the unit-cell matrix;
- generic atomic views preserve the concrete `ExpandedAtom` or `MolecularAtom`
  type;
- molecular views produce a finite `NeighborGraph` without periodic metadata;
- periodic references resolve to the correct translated coordinates;
- graph edges have correct reverse vectors and translations;
- boundary-crossing neighbors are found without duplicating graph nodes;
- a highly skewed triclinic fixture finds every neighbor within the cutoff
  exactly once;
- coordination numbers are invariant under equivalent choices of reference
  cell;
- real CIF and SHELX fixtures traverse the complete structure-to-neighbor path;
- the built wheel exposes the intended imports in a clean environment.

No public PyPI publication is part of this milestone.
